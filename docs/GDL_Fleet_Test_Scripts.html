—How to use this

Read this page once before the first test. It will save arguments later.

Every test has the same shape

PartWhat it means
IDFL-05-03 — suite 5, test 3. Quote it when raising a defect.
Run asLog in as this user. Testing as Administrator proves nothing about permissions, because Administrator bypasses them.
StepsDo these in order. If a step fails, stop and record where.
ExpectedGreen means it should succeed. Red means it should be refused — and the test fails if the system lets you through.
Half these tests are meant to fail

A negative test passes when the system stops you. If you can double-book a vehicle, approve another site's request, or submit a fuel claim with no bill attached, that is a defect, however convenient it feels at the time.

When the system refuses you, read the message. It should name the record it is protecting and tell you what to do. A refusal with an unhelpful message is worth raising even though the block itself worked.

Recording a result

Each test ends with a result line. Tick one, initial it, and write the date. If you tick Fail, write what actually happened — "rejected" on its own cannot be investigated. Screenshot anything surprising.

Blocked means you could not run it, usually because a prerequisite is missing. That is not a defect in the module; it belongs on the prerequisite list.

One trap worth knowing before you start

Submit, don't just save. In ERPNext a saved record is a draft and counts for nothing — it will not appear in reports, will not block a double booking, and will not carry a balance forward. Several tests look broken until you notice the record was never submitted.

Setting a password so you can test as a real user

The fourteen fleet users exist but have no passwords. From the bench terminal:

bench --site gdl-staging.localhost set-password Administrator jamjee.mto@gdl.test

Do the same for jamjee.user@gdl.test, dochula.mto@gdl.test and headoffice.mto@gdl.test — those four cover every permission test in Suite 5 and Suite 14.

Two things staging will not do

No email leaves the site and the scheduler is paused. Both are deliberate — staging came from a real database and must not contact real people. So reminder emails will not arrive during testing. Suite 9 tests the renewal status and the configuration of the alerts instead, which is what can honestly be verified here.

Suggested order

Run 1, 2, 13 first — they need nothing and confirm the system is sound. Then set passwords and run 5, 6, 14, which cover the change GDL actually asked for. Create drivers and run 3, 4, 10, 11. Leave 8 and 12 until the approver role and the stock items exist.

Raising a defect

Quote the test ID, say what you expected and what happened, and attach a screenshot. "FL-05-03 failed — the Dochula MTO was able to accept a Jamjee request" can be investigated in minutes. "Approvals are broken" cannot.

Two results that are not defects

No email arrived. Outbound mail is muted and the scheduler is paused on staging, deliberately, because this database came from a real system. Test the alert configuration (FL-09-05) instead.

A blocked test. Missing drivers, suppliers or settings are GDL's to supply. Record them as Blocked and they become the prerequisite list, not the defect list.

What is knowingly not covered

SAP integration. The blueprint names it under Tyre Mileage. Nothing is built and nothing is testable; it needs a scoping session on direction, transport and which documents cross.

The five-stage approval chain. It exists, switched off. If GDL ever turns it on, Suite 6 needs rewriting for the longer chain.
